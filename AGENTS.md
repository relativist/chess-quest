# Правила выполнения задач

## Классификация задачи

Перед началом работы определи размер и сложность задачи.

Считай задачу крупной, если выполняется хотя бы одно из условий:

* пользователь пишет «реализовать фичу», «добавить функциональность», «спроектировать», «провести рефакторинг» или использует формулировку с аналогичным смыслом;
* требуется изменить несколько модулей или слоёв приложения;
* необходимо сначала исследовать архитектуру или существующий поток данных;
* задача затрагивает API, базу данных, Kafka, Spark, безопасность, конкурентность или транзакции;
* возможны независимые направления исследования или реализации;
* задача требует нескольких этапов: исследование, планирование, реализация, тестирование и итоговая проверка.

Не полагайся только на точное совпадение ключевой фразы. Определяй сложность задачи по её смыслу и области изменений.

## Крупные задачи

Для крупной задачи главный агент должен выступать координатором.

Перед изменением кода:

1. Проанализируй требования.
2. Определи область изменений и основные риски.
3. Раздели задачу только на независимые подзадачи.
4. Используй исследовательских субагентов для изучения разных частей проекта.
5. Дождись результатов исследования.
6. Самостоятельно составь общий план реализации.

Используй субагентов следующим образом:

* `terra_explorer` — исследование кодовой базы, зависимостей, конфигурации и существующей реализации без изменения файлов;
* `terra_worker` — реализация чётко ограниченных независимых частей и написание тестов;
* `fast_worker` — простые механические задачи, поиск однотипных мест, документация, DTO, мапперы и небольшие проверки.

Не запускай субагентов только ради параллелизма. Делегирование должно уменьшать объём контекста главного агента или ускорять независимые работы.

Не разрешай нескольким агентам одновременно изменять один и тот же файл или тесно связанные участки кода.

Не делегируй окончательные архитектурные решения.

После завершения субагентов главный агент должен:

* объединить результаты;
* проверить совместимость изменений;
* проверить полный diff;
* устранить конфликты и несогласованности;
* запустить итоговые тесты;
* проверить выполнение исходных требований;
* представить единый итоговый отчёт вместо необработанных отчётов субагентов.

## Небольшие задачи

Для небольшой, локальной и однозначной задачи работай в основном потоке без субагентов.

Считай задачу небольшой, если она:

* затрагивает один или несколько тесно связанных файлов;
* не требует архитектурного исследования;
* не содержит независимых направлений работы;
* является локальным исправлением, небольшим рефакторингом или простым добавлением;
* может быть безопасно выполнена и проверена одним агентом.

Не запускай субагентов для:

* исправления опечатки;
* изменения одной настройки;
* небольшого SQL-запроса;
* добавления одного поля;
* локального исправления одного метода;
* простого unit-теста;
* форматирования или обновления документации.

Если небольшая задача в процессе оказывается сложной, остановись, переклассифицируй её как крупную и примени многоагентную схему.

## Явное управление пользователем

Явное указание пользователя имеет приоритет над автоматической классификацией.

Фразы:

* «используй субагентов»;
* «раздели задачу между агентами»;
* «запусти исследовательских агентов»;

означают, что необходимо применить многоагентную схему.

Фразы:

* «сделай сам»;
* «не используй субагентов»;
* «это маленькая правка»;

означают, что нужно выполнить задачу в основном потоке без делегирования.

## Ориентиры по проекту Chess Quest

### Онлайн-режим

План и принятые решения находятся в `docs/online-mode-plan.md`. Основные точки входа:

* `src/app/online/page.tsx` и `src/components/online-lobby-client.tsx` — lobby, presence и вызовы;
* `src/app/online/game/[matchId]/page.tsx` и `src/components/online-chess-game-client.tsx` — интерфейс партии;
* `src/app/api/online/**` — HTTP API lobby, challenges, match, moves, magic, draw, surrender и rematch;
* `src/lib/online/domain.ts` и `src/lib/online/match-domain.ts` — чистые правила и расчёты;
* `src/lib/online/repository.ts` — presence и вызовы;
* `src/lib/online/match-repository.ts` — сервер-авторитетное состояние партии, часы, ходы, магия, завершение и рейтинг;
* `src/lib/online/rematch-repository.ts` — жизненный цикл реванша;
* `src/lib/online/server-auth.ts` — обязательные PostgreSQL, сессия и роль `PLAYER`;
* `src/lib/online/constants.ts` — общие лимиты и таймауты;
* `prisma/schema.prisma` и миграции `20260711120000_add_online_mode`, `20260713023000_add_online_rematch_source` — модель хранения.

Онлайн-партия является сервер-авторитетной. Клиент не должен самостоятельно изменять FEN, часы, монеты, результат или рейтинг: он отправляет команду и применяет возвращённый snapshot. Конкурентные команды защищены полем `version`, транзакциями и идемпотентными событиями.

Ключевые инварианты:

* presence и challenge живут 30 секунд и обновляются polling/heartbeat;
* у игрока может быть только один активный матч;
* цвета назначаются случайно при принятии вызова;
* стартовые часы — по 10 минут, матчевые монеты — по 500;
* часы продолжают идти при закрытой вкладке; reload/reconnect восстанавливает матч из БД;
* undo в онлайн-режиме отсутствует;
* surrender сразу завершает матч;
* каждый игрок может предложить ничью не более трёх раз;
* победителю начисляется `+1`, проигравшему `-1`, но рейтинг не опускается ниже нуля;
* применение рейтинга и повтор сетевой команды должны быть exactly-once;
* после результата финальная доска остаётся доступна, затем возможны возврат в lobby или реванш.

### Base path и клиентская навигация

Production может работать с `NEXT_PUBLIC_BASE_PATH=/chess-quest`. Учитывай различие API браузера и Next.js:

* для `fetch`, обычных URL ресурсов и нативных ссылок используй `publicPath(...)`;
* в `router.push`, `router.replace` и `next/link` передавай внутренний путь без base path, например `/online/game/...`; Next.js добавляет base path сам;
* не передавай результат `publicPath(...)` в router или `Link`, иначе получится `/chess-quest/chess-quest/...`.

Production-проверка:

```bash
NEXT_PUBLIC_BASE_PATH=/chess-quest npm run build
```

Для ручного standalone-теста после build синхронизируй `.next/static` в `.next/standalone/.next/static`, иначе браузер может получить устаревшие чанки.

### Проверка онлайн-режима

Быстрый обязательный набор:

```bash
npm run typecheck
npm run lint
npm test
NEXT_PUBLIC_BASE_PATH=/chess-quest npm run build
```

`src/lib/online/repository.integration.test.ts` запускается только при заданном `ONLINE_INTEGRATION_DATABASE_URL`. Эти тесты требуют отдельную PostgreSQL с применёнными Prisma-миграциями и проверяют конкурентное принятие вызова, версии ходов, exactly-once рейтинг, ничью, surrender, timeout и rematch. Не направляй интеграционные тесты на пользовательскую или production-базу.

Для значимых изменений онлайн-потока дополнительно проверь две независимые браузерные сессии: появление игроков, challenge/accept, противоположную ориентацию досок, синхронизацию хода, reload/reconnect, ничью, surrender, финальную доску и rematch. На ширинах 320, 375, 390 и 768 px не должно быть горизонтального overflow.

### Рабочий процесс

Рабочее дерево может содержать незакоммиченные изменения пользователя. Не удаляй и не откатывай несвязанные файлы. Не выполняй commit или push без прямой просьбы пользователя. Если в репозитории доступна база `bd`, после проверки закрывай завершённую задачу; если базы нет, не запускай `bd init` без отдельного запроса.
